# TASK-083

- Timestamp: 2026-08-12
- Original request: "the recomile after answering still dont work" — user, after testing TASK-031's fix for Confirm & Recompile.
- Priority: P1 (bug, second report on this exact feature)
- Status: CLOSED — bug fixed (stale unresolved items now pruned on recompile); requirement 3's "specialists don't react to free-text answer content" is a confirmed real limitation, honestly documented rather than fixed (see state/CANONICAL_STATE.md TASK-083 section)
- Classification: bug

## Investigation already done (confirm this, don't re-derive from scratch)
Direct reproduction via a throwaway vitest script against `resumeAndRecompile` (packages/compiler/src/resumeAndRecompile.ts) confirmed:
1. Answering an unresolved item via `mergeAnswer` correctly adds a new `kind:'user'`/`source:'user-answered-question'` item to `userRequirements` — this part works.
2. Calling `resumeAndRecompile` on the result correctly preserves that answered item and correctly re-runs all specialists/critique/conflict/synthesis.
3. **BUG:** the ORIGINAL unresolved item (the one that was just answered) is STILL present, unchanged, in `compiled.assumptions` with `kind: 'unresolved'` after the recompile — it is never cleared/removed even though a matching answer now exists. `reconstructStateFromCompiled` flattens every `kind:'unresolved'` item from the input `compiled` straight into the new `ambiguities` array with no check for whether a matching answer already exists. Since `ambiguityDetection` is deliberately not re-run (by design, per TASK-031), nothing else ever removes it either.
4. Likely user-visible symptom: even though the DecisionsPanel UI's `isAnswered()` check (apps/desktop/src/components/DecisionsPanel.tsx) does text-match answered items against unresolved items and correctly hides genuinely-matched ones from the "Unresolved" section in most cases, this is fragile (relies on exact evidence-text matching) and — more importantly — a SECOND recompile (answering another item, hitting Confirm & Recompile again) re-processes an ever-growing, never-pruned `ambiguities` list, and the specialists/critique/conflict genuinely don't do much with plain free-text answers that don't happen to match their own keyword triggers, so from a user's perspective the recompiled output can look identical to before — "doesn't work."

## Requirements
1. Fix `reconstructStateFromCompiled` (or `resumeAndRecompile`, whichever is the right layer) in `packages/compiler/src/resumeAndRecompile.ts` so that an unresolved item with a matching answer already present in `userRequirements` (same matching logic as the UI's `isAnswered()` — evidence referencing the unresolved item's text) is NOT carried forward into the reconstructed `ambiguities` array on a recompile. It should be dropped from the unresolved pool (the answer supersedes it), consistent with the append-only provenance discipline (the original item itself is never mutated, it's just excluded from the NEW state's `ambiguities` going forward — read `mergeAnswer.ts` and the UI's `isAnswered()` implementation for the exact matching convention already established, reuse it exactly, don't invent new matching logic).
2. Verify this fix doesn't affect ARCHITECT/QUICK/MASTER's normal (non-resume) `ambiguityDetection` behavior at all — this is scoped entirely to the resume path.
3. Investigate the second half of the likely symptom: are the existing specialists/critique/conflict actually capable of producing MEANINGFULLY different output in response to typical free-text answers, or do they only react to keyword-matchable content? If the latter, this may be a real, harder limitation worth documenting honestly (per this project's own "no fake functionality" discipline) rather than something fixable in this task — investigate and report findings clearly; do not silently declare success if the underlying specialist reactivity is genuinely weak for typical answers. If there's a cheap, well-scoped improvement available (e.g. ensuring critique's near-duplicate/low-confidence rules meaningfully reconsider items now that context changed), implement it; if a real fix would require deeper specialist redesign, document it as a known limitation instead of overpromising.
4. Add tests in packages/compiler/test/ proving: an answered item's original unresolved flag is genuinely excluded from a recompile's ambiguities/assumptions, a SECOND recompile (answer another item, recompile again) doesn't reintroduce or duplicate stale unresolved entries, and confirm via direct evidence (test assertions, not just "doesn't throw") that the recompiled output differs meaningfully from the pre-answer state in at least the unresolved-count sense even if specialist reactivity for generic answers is limited.
5. Must not break any pre-existing tests.
6. `tsc --noEmit` clean on all 3 packages, `vite build`/`cargo build` clean if touched.
7. Update `state/CANONICAL_STATE.md` and task/queue status, being HONEST in the writeup about what was fixed vs. what remains a genuine limitation (per requirement 3) — do not mark this DONE with an overstated claim if the underlying "specialists don't semantically understand free-text answers" limitation isn't actually resolved, since that's the second time this feature has been reported broken and overclaiming a third time would be worse than an honest partial fix.
