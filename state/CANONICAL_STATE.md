## Fix "Confirm & Recompile" — resume-based recompile, not a from-scratch re-run (TASK-031)
- **Purpose**: user-reported bug immediately after testing TASK-030: "the recompile is buggy resets answers and doesnt actually recompile." This task REPLACES TASK-030's recompile mechanism with a correct one — TASK-030's Part B (Export Project Handoff Folder) is untouched and still correct.
- **Root cause (confirmed)**: TASK-030's `handleConfirmRecompile` built a synthetic augmented-text string (`buildAugmentedInput`: original raw input + each answered Q&A appended as a plain sentence like `"${question}: ${answer}."`) and fed it into a completely fresh `runArchitectPipeline`/`runQuickPipeline`/`runMasterPipeline` run. - **Fix — `packages/compiler/src/resumeAndRecompile.ts`** (new, exported from `index.ts`): `reconstructStateFromCompiled(compiled: CompiledPrompt, rawInput: string): PipelineState` builds a `PipelineState` directly from an EXISTING `CompiledPrompt` instead of raw text — flattens all 6 category arrays back into parallel `requirements`/`requirementCategories` arrays (every answered item, still `kind:'user'`, flows straight through and is preserved), routes any item still `kind:'unresolved'` into `ambiguities` instead of `requirements` (mirroring `ambiguityDetection`'s original output shape, since `synthesis`/`critique` both expect ambiguities to live there), reuses `compiled.domain` and `compiled.architecture` verbatim (never re-derived), and recovers `taskType` by parsing it back out of `compiled.objective` (the exact string `synthesis` encoded it into) rather than re-running `intentAnalysis`. `resumeAndRecompile(compiled, rawInput, mode, options?)` then runs this reconstructed state through the SAME specialist-pass/critique/conflict/synthesis/outputValidation stage functions `runArchitectPipeline`/`runQuickPipeline`/`runMasterPipeline` already use (imported directly, no duplicated logic reinvented) — for `'architect'`: all 7 specialists -> critique -> conflict -> synthesis -> outputValidation; for `'quick'`: synthesis -> outputValidation only (mirrors `runQuickPipeline` skipping specialists/critique/conflict entirely); for `'master'`: all 7 specialists -> the same loop-until-dry critique/conflict/alternativeGeneration/decisionScoring cycle (identical dry-check/`maxRounds` logic, copied verbatim from `runMasterPipeline`) -> synthesis -> outputValidation. Deliberately never re-runs `intentAnalysis`/`domainDetection`/`requirementExtraction`/`ambiguityDetection` — those already ran once against the real raw input; re-running them against a synthetic string was exactly the bug. `runArchitectPipeline`/`runQuickPipeline`/`runMasterPipeline` themselves are completely unmodified (zero lines changed) — `resumeAndRecompile` is strictly additive, so every pre-existing test for normal from-scratch compiles passes unchanged.

## Verifier recommendation for next work (post-TASK-004, N=3 specialists proven)
With ARCHITECT, TECHNICAL, and UX all real and independently verified to merge cleanly via `synthesis.ts`'s append-only pattern, there are two credible next moves: a fourth specialist (QA/SECURITY/CONSTRAINT/CREATIVE), or building the real critique/conflict-detection engine (`critiquePassthrough`/`conflictPassthrough` are still no-op passthrough stages sitting between the specialist passes and synthesis).

**Recommendation: build the critique/conflict engine next, not a fourth specialist.** Reasoning:
- The registry/pass-stage pattern has now been proven three times (architect→technical, technical→ux) with zero surprises at each step — a fourth specialist would very likely just reconfirm a pattern that's no longer in doubt. That's low marginal information for the implementation cost.
- There is now genuine cross-specialist material worth reasoning over: e.g. for "make me a horror game," TECHNICAL's multiplayer-networking constraint and UX's pacing/tension-curve recommendation are exactly the kind of items a conflict engine should be able to relate (does a networked multiplayer mode undercut a carefully paced single-player tension curve? does UX's "remappable controls" recommendation interact with TECHNICAL's platform/input constraints?). Before N=3 this cross-talk was thin; now it's real.
- The passthrough stages are currently pure no-ops sitting in the pipeline's critical path — every additional specialist added without touching them increases the gap between "what the architecture implies should happen here" and "what actually happens," which compounds risk the longer it's deferred.
- Risk acknowledged: conflict detection is a genuine design problem (what counts as a conflict, how it's surfaced without becoming noisy) — bigger and fuzzier than adding another specialist. But that is exactly why it should be tackled now, deliberately, rather than backed into later after a fourth or fifth specialist has added even more surface area to reconcile.
- A fourth specialist remains a reasonable and cheap fallback if the user wants to defer the harder design problem — SECURITY or CONSTRAINT would be the next logical picks — but it is the lower-value option at this point given how proven the registry pattern already is.
This is a recommendation only; no implementation was started for either option.
